NOC Runbook

Bare virtual machine to a protected website, for an engineer who has never seen this product and will have nobody to ask on the day.

Every command here was executed on a fresh Ubuntu 24.04 VM (172.16.21.101) on 2026-08-14, in this order. Every quoted output is the real one. Where a step has a trap, it is a trap that actually occurred.

00 What you are deploying

A reverse-proxy security gateway. It sits in front of a website. Visitors reach the WAF, the WAF inspects the request, and only acceptable requests reach the real server.

Visitor → ESDSWAF → Origin server ↳ attacks stopped at the WAF

Two addresses matter, and confusing them is the usual first mistake.

AddressWhat it is
Hostname visitors type portal.example.com — the WAF matches sites by Host header alone, so this must be exact.
The origin 10.20.30.40:8080 — where the application runs today. Must be reachable from the WAF host.

-registry for any ESDS-internal VM. It ships no container images at all — the installer pulls all ten from Harbor, needing no credentials because that project is readable inside the ESDS network. 401 is correct

401 is a registry's normal answer to an unauthenticated request and proves the VM can reach it. A timeout or 000 means blocked. -offline is for a customer datacentre, which cannot reach Harbor whether or not it has internet — Harbor sits on 172.16.23.2, which does not route from outside ESDS.

02 Install Docker

Skip if docker --version already works.

curl -fsSL https://get.docker.com | sh
systemctl enable --now docker

Verify — both must answer:

docker --version          # Docker version 29.7.2, build a7dcaa6
docker compose version    # Docker Compose version v5.4.0

03 Get the package onto the VM

Either copy it across with scp, or download it from GitLab — Deploy → Package Registry → esdswaf. You need both the archive and its .sha256.

cd /root
sha256sum -c ESDSWAF-v1.0.2-online.tar.gz.sha256    # must print: OK
tar -xzf ESDSWAF-v1.0.2-online.tar.gz
cd ESDSWAF-v1.0.2
Do not skip

Verify the checksum. A truncated download fails later, during image loading, in a way that looks like a product fault.

If you were given the offline bundle in parts, reassemble first — the result is byte-identical and the checksum proves it:

cat ESDSWAF-v1.0.2-offline.tar.gz.part-* > ESDSWAF-v1.0.2-offline.tar.gz
sha256sum -c ESDSWAF-v1.0.2-offline.tar.gz.sha256

05 Install

sudo ./install.sh

It asks three things: the hostname clients will use, an administrator email, and the topology — choose 1, standalone. Every password, key and certificate is generated for you. You are never asked to invent a secret.

Unattended:

sudo WAF_HOSTNAME=172.16.21.101 ADMIN_EMAIL=you@esds.co.in \
     ./install.sh --non-interactive

Ten steps, roughly six minutes. It ends with:

  Installation successful

    Version        Swaraj Kavach v1.0.2
    Username       admin@sentinel.local
    Password       6c1a48cb969314feb230ce64072348d3afba849a67c59f0534ac480437a7786b

The single most important thing in this document

That password cannot be changed. Ever.

This build has no password-change screen and no reset endpoint — the user API accepts role and status only. That credential is the only way into the console for the life of the installation.

It is saved for you in /opt/sentinel/current/.env (mode 0600), so it survives container recreates, upgrades and rollbacks:

sudo grep SENTINEL_BOOTSTRAP_ADMIN_PASSWORD /opt/sentinel/current/.env

Back that file up today, somewhere outside this VM. It holds every secret for the deployment. Lose it and the installation must be rebuilt from scratch.

Create a second administrator now — Settings → Team Members → Add User. It is your only redundancy. No email is sent: you set the password (minimum 12 characters) and pass it on yourself, and it cannot be changed later either.

06 Verify

sudo ./verify.sh

Real output on a fresh install:

  18 passed, 0 failed, 2 warnings

  All checks passed. Review the warnings above.
  Note: enforcement was NOT verified — this run proved the stack is running,
  not that it blocks anything.
Expected

Both warnings are correct before you add a site: no sites configured yet and enforcement not tested. A 502 from the WAF before the first site exists is right, not broken — there is no upstream to forward to yet.

0 failed is the number that matters. If Control plane → database fails, stop: the control plane runs without a database rather than exiting, and every login returns 503 while docker ps looks perfectly healthy.

07 Reach the console

The console is bound to 127.0.0.1 only, deliberately. It is a security appliance's admin UI; on 0.0.0.0 it would be exposed to the whole office network. https://<vm-ip>:9443 will not work, and that is correct.

ssh -L 9443:127.0.0.1:9443 root@172.16.21.101

Then open https://127.0.0.1:9443

  • Expect a certificate warning — the WAF issued its own. Advanced → Proceed.
  • Log in with admin@sentinel.local and the password from step 05.
  • A 500 on first load is usually a cached error: hard-reload (Ctrl+Shift+R) or use an incognito window.

Ports 80 and 443 are published on all interfaces — that is the traffic path.

08 Put a site behind the WAF

The fastest correct way, on the VM:

sudo ./first-site.sh

It asks for the visitor hostname, origin address and origin port; checks the origin is reachable from inside the WAF's network; validates the config against the data plane before storing it; confirms the data plane actually loaded it; then proves the WAF inspected a live attack. Real output:

==> Confirming the data plane loaded it
  ✓ data plane loaded it — now serving 4 site(s), was 3

==> Proving the WAF inspects traffic for this site
  ✓ normal request -> 302 (the origin answered; a redirect counts)

==> Confirming the rule engine inspected it
  ✓ attack request -> 302, and the WAF recorded it:
      rule 942100  score 30/10  SQL Injection Attack Detected via libinjection

Use --dry-run to see exactly what it would create without creating it.

Doing it in the dashboard instead

Sites → New Site. Two things will catch you out.

Trap 1 — the wizard will not save

Turn OFF “Serve HTTPS” on the Front Service step (or pick 🚫 No certificate) unless the hostname is publicly resolvable. New sites default to automatic Let's Encrypt certificates, and the wizard silently refuses to save without a contact email — a red toast reading “An email is required for automatic certificates”. Let's Encrypt cannot issue for an internal name regardless.

Trap 2 — you cannot switch later

Use Advanced mode if the application needs anything non-default. Easy mode's Reverse Proxy step has exactly three controls: host, port, upstream HTTPS. Body size, timeouts, URI/header limits, allowed methods, WebSocket, health check and origin SNI are all Advanced-only, and switching an existing site is not offered. Decide up front.

Four limits that will break real applications

These reject in every mode, including learning:

09 Leave it in LEARNING mode

Do not switch a customer site to blocking on day one. Every detection figure this product publishes comes from a synthetic corpus. Nobody has measured how often it would wrongly block that customer's users.

Learning mode detects, scores and records — and lets the request through:

rule_ids "942100,942180,942330,942390,9900100"
decision "Log"   block_reason "anomaly score 30 >= threshold 10"   status 200

Blocking mode, same request:

sqli: 403    xss: 403    traversal: 403    normal: 200

Going live

  1. Run for a full business cycle — 1 to 2 weeks, including month-end if traffic changes then.
  2. Measure: /opt/sentinel/current/scripts/fpr-report.sh 168
  3. Only when that is clean, switch to blocking, then confirm: 
    SENTINEL_VERIFY_HOST=portal.example.com sudo ./verify.sh
    It must say SQL injection → 403 — blocking is ENFORCED.
Known defect

A newly created site is matchable before it is inspected. Rule engines are rebuilt on a 5-second poll and then compiled; until that lands the site proxies traffic with rule_matches=0. Never conclude “it does not block” from a test in the first ~10 seconds, and do not create a site directly in blocking mode — it fails open through that window.

12 Removing it

sudo ./uninstall.sh          # keeps data volumes, .env and certificates
sudo ./uninstall.sh --purge  # destroys everything, including the database

After a plain uninstall the data survives, so reinstalling must reuse the existing secrets:

sudo ./install.sh --force

--force is required because the .env deliberately survived — a plain install.sh stops rather than regenerate secrets against a database that already exists, which would lock you out of your own data.
